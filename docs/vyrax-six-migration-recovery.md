# Vyrax six-file migration and mail safety, staged only

This is a release procedure, not permission to touch production. PR 50 at the reviewed exact SHA needs a fresh webqa AGREE and Leo's explicit go. No customer mail, migration, Worker deploy, or live flag is authorised by this file. The six new SQL versions run in filename order, 20261116000000 through 20261119000000. Existing production has no `supabase_migrations` schema (release preflight, 21 Nov 2026); `email_automation_control.enabled=true` and three original email cron jobs are active. The two original Worker secret gates cannot be inspected. Never presume they are off.

## Before any live write, release only

1. Confirm current live build, deployed Worker version, main SHA, database backup/PITR window, exact reviewed god PR head and Leo go. Record the three active cron names and `email_automation_control.enabled` by read-only queries, not from this document. Do not use `supabase db push` against the live database yet.
2. Run `psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f scripts/vyrax-six-migration-reconcile.sql` **read-only** and archive its output. Ten original versions must be `PRESENT`, all six new versions `ABSENT`, with no `MIXED_STOP`. This proves the current schema markers, not that a named migration historically ran. Verify the individual definitions and constraints against the original migration files. Any mismatch, earlier hotfix, pre-existing new object, partially applied version, or ledger already present means stop for a tailored plan. Never mark an absent version applied or run all sixteen migrations blindly.
3. Verify eight expected pre-change function signatures exist and the three named pre-change CHECK constraints exist. Save a read-only, per-database snapshot before up: `psql "$DATABASE_URL" -X -A -t -v ON_ERROR_STOP=1 -f scripts/vyrax-six-recovery-snapshot.sql > "$SECURE_RELEASE_DIR/vyrax-before.sql"`. Inspect the file, it must have eight `CREATE OR REPLACE FUNCTION` definitions, three `ADD CONSTRAINT` statements, the RLS state and original grants. Retain it privately with the incident/rollback pack. No customer rows or secrets are in this schema-only file. Without the snapshot, stop.
4. If and only if the first ten markers and definitions match the live baseline, release may initialise its missing ledger by `supabase migration repair --status applied --remote="$DATABASE_URL" --yes 20260928151737 20261002000000 20261002010000 20261003000000 20261006000000 20261103000000 20261105000000 20261105230000 20261107000000 20261114010000`. This is a live metadata write, gated with the migration release. Read back `supabase_migrations.schema_migrations` and require exactly those ten rows. Test of this exact repair on a ledgerless disposable Supabase Postgres database is in `scripts/vyrax-six-recovery-test.sh`.
5. `supabase db push --remote="$DATABASE_URL" --skip-vault --dry-run` must list **only** the six versions. With explicit go, release may apply only those six. This does not activate the new flows: `public.email_new_flow_control` creates three rows (`packed`, `feedback`, `winback`) with `enabled=false`, independently of the already-true legacy automation switch. New packed trigger and feedback/winback scheduler wrappers return before enqueue. New kinds are rejected by eligibility, even explicit claim calls and rechecks. No other migration or secret turns these on. Leave them false, including after deploy. Existing order and marketing flows are not disabled by this change; check their separate release controls and live send policy independently.
6. Read back sixteen ledger rows, six new schema fingerprints `PRESENT`, three flow rows all false, and the cron schedule. Do not send a test email or place a real order. Deploy/merge is release's job only after exact-SHA review and Leo go.

## Recovery, release only

If any up fails, stop the Worker rollout and keep new flow controls false. Check whether the failed migration was transactional, compare ledger and all fingerprints, and tailor recovery to the actual partial state. Do **not** run the down files against a partial state. If all six were applied and no new-kind jobs exist, use the saved snapshot from this same database and the same reviewed commit:

`psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f scripts/vyrax-six-recovery-down-prefix.sql -f "$SECURE_RELEASE_DIR/vyrax-before.sql" -f scripts/vyrax-six-recovery-down-suffix.sql`

This is a single transaction, fails closed if any new flow is enabled or any packed/feedback/winback outbox row exists. It unschedules the expiry cron, removes the packed trigger and wrappers, restores prior function definitions, CHECK constraints, ACL and RLS state from the actual pre-up database, and drops empty new structures. It retains `customer_interactions` if it has rows and `orders.expired_at` if populated, rather than deleting customer data. If either is retained, inspect dependencies and document this additive residue; do not call the schema exactly reverted. An incident with new jobs or sends needs a bespoke data-preserving rollback and no automated down. Restore the prior Worker version separately, then reconcile payment and delivery events before any replay.

After successful down, the ledger still records six applied versions. With separate release authorisation, mark **only** the six as reverted using `supabase migration repair --status reverted --remote="$DATABASE_URL" --yes 20261116000000 20261117000000 20261118000000 20261118010000 20261118230000 20261119000000`; verify ten rows remain. Do not reapply without a new review. This metadata correction is not part of the SQL transaction, so if repair fails, stop and report schema/ledger disagreement. `scripts/vyrax-six-recovery-test.sh` reproduces initial baseline, ledger absence, repair, six ups, guarded down and fingerprint verification on a disposable DB. It never uses live credentials.
