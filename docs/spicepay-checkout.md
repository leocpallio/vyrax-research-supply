# Vyrax SpicePay checkout (OFF by default)

This is **Vyrax-only** code. Do not copy the Peptide Pro/UKPL merchant, keys, profile, webhook secret, domain or fulfilment settings. No credentials are checked in. The catalogue-only checkout screen remains the default and server checkout rejects requests unless explicitly enabled. The former browser-side enquiry INSERT was removed because the restricted orders table cannot accept untrusted client-created orders; enquiry intake remains closed. No automatic email, stock reservation or dispatch exists here; payment success alone is **not** authorisation to fulfil an unavailable product.

## Before enabling

1. Verify Vyrax legal/trading readiness, product permissions, actual stock/availability, tracked shipping, support inbox, refund handling and the SpicePay account's exact Vyrax merchant + shop profile. The source catalogue is the server authority for prices and offers, not a live inventory ledger. Out/preorder strengths are rejected; untracked `available` strengths are *not* proof of stock. Do not enable public checkout without a stock/fulfilment control and a human process for oversell/refunds.
2. Apply `supabase/migrations/20261002000000_spicepay_checkout.sql` to the **Vyrax** Supabase project, verify anonymous/authenticated INSERT/UPDATE/DELETE on `orders` is denied. Existing enquiries remain; authenticated owners retain column-scoped SELECT for the existing account order history, but guest tokens, delivery addresses, payment IDs and other sensitive columns must be denied. Test both owner and non-owner RLS.
3. Set these **server-only** environment values on the Vyrax SSR server (never `VITE_`, never client/UKPL secrets): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `VYRAX_SPICEPAY_SECRET_KEY`, `VYRAX_SPICEPAY_PROFILE_ID`, `VYRAX_SPICEPAY_MERCHANT_ID`, `VYRAX_SPICEPAY_WEBHOOK_SECRET`, `VYRAX_SPICEPAY_MODE=test` (or `live`), `VYRAX_CHECKOUT_ORIGIN=https://<exact-Vyrax-origin>`. All are mandatory. `VYRAX_SPICEPAY_CHECKOUT_ENABLED` defaults off. Only after controlled E2E tests, set it to `true` on the server and build with `VITE_SPICEPAY_CHECKOUT_ENABLED=true` for the payment UI. Both flags are required. Do not set either on a public deployment until signed webhook + database migration + controlled test succeeded. Keep `MODE=test` during test; mode is always explicitly sent to SpicePay, never delegated to a processor default.
4. In the **Vyrax** SpicePay Control Center add `https://<exact-Vyrax-origin>/api/spicepay-webhook` as an HTTPS webhook endpoint. Subscribe at minimum to `payment_succeeded`, `payment_failed`, `payment_processing`, `payment_cancelled`, `payment_expired`, `action_required`. Store that endpoint's signing secret as `VYRAX_SPICEPAY_WEBHOOK_SECRET`. Webhook requests require the `X-Webhook-Signature-512` hex HMAC-SHA512 signature on the unmodified raw request bytes. This TanStack server route does not require a Supabase JWT; do not put it behind a body-transforming middleware. Return URL is `/checkout/return?order=<id>` and **never marks paid**.
5. Controlled E2E: with an isolated test-mode Vyrax merchant and test payment, verify the provider request's amount in pence, GBP, merchant/profile, `test_mode:true`, and hosted URL; compare DB order amount/status. Deliver a valid signed `payment_succeeded` event and verify one paid transition/event row; redeliver same ID and a different success ID and verify no second transition. Test wrong signature, amount, merchant, currency, payment ID and mode: none may mark paid. Test failed/processing/cancelled arriving before/after success, webhook retry while binding, and browser return without webhook. Confirm status endpoint rejects missing/wrong guest token and no service key appears in browser bundles. Do **not** perform live transactions until a separate approval.

## Design and operations

`POST /api/checkout` accepts only catalogue slug, strength and integer quantity plus name/email/phone/UK address and research acknowledgement. It computes GBP pence using approved catalogue prices, B2G1, spend tiers and delivery; client prices/totals are ignored. It writes a `creating` order first, asks SpicePay to create a hosted payment with an explicit mode, then binds the payment ID and only then returns the checkout link. A failed processor request/binding leaves a `creating` order for manual reconciliation; **never send a payment link when binding fails**. If a webhook beats binding it gets 503 so SpicePay retries. Do not automatically retry a failed creation on the same order unless a safe processor idempotency strategy has been verified.

`POST /api/spicepay-webhook` validates HMAC, merchant, payment ID, amount, currency, test flag and success status, then calls a service-role-only atomic SQL RPC with event-ID dedupe and conditional paid transition. Other correctly matched events are recorded but do not demote or fulfil an order. Signed mismatch returns non-2xx for investigation. Test orders can become `paid` in the ledger but must never be fulfilled as live orders. `GET /api/order-status` needs both UUID order ID and random UUID guest token and exposes only status/amount/currency/mode. Token is kept in browser sessionStorage, not in the processor return URL; checkout return cannot confirm anything. There is no rate limiter in this repo: place the checkout/status endpoints behind an appropriate edge abuse/rate control before opening publicly.

No deployment, database migration application, merchant credential validation or real payment has been performed by this code change. Keep the flags OFF pending those gates.
