# Vyrax Labs email system: readiness and wiring

## Current status (verify again before changing the gates)

- `src/lib/email/templates.ts` renders HTML and plain text from one Vyrax brand wrapper. Drafts cover enquiry acknowledgement, owner enquiry alert, payment pending/confirmed, packed/dispatched, cancellation/refund, support acknowledgement and auth confirmation/reset. Dynamic HTML copy is escaped. Only same-origin auth links become clickable; external tracking links are not inserted blindly. An enquiry estimate is not a receipt.
- `src/lib/email/send.server.ts` is a server-only Resend transport with an idempotency header. It fails closed without server environment `RESEND_API_KEY` and `VYRAX_EMAIL_FROM`, and requires a well-formed sender on `vyraxlabs.co.uk`. No key is committed or used here. A key previously disclosed in chat must be rotated, not reused. Never use another brand's key.
- **No application messages are wired live.** There are no `sendTransactional` callers in the app. `site.email` remains null and `site.enquiriesLive` false; `/contact` can only open a `mailto:` draft once the support address has been verified and configured. Supabase Auth/Lovable Cloud owns signup mail; the drafts here do not replace its provider templates. A server-side SpicePay checkout and signed paid-status webhook exist in `src/lib/checkout.server.ts`, but are deliberately closed by server configuration; neither currently triggers email. The old direct browser-side enquiry INSERT was removed. No server-side enquiry intake, fulfilment email trigger, support ticket store, durable email outbox, or unsubscribe/recovery automation exists.
- DNS observations during audit are not proof of delivery: authoritative Cloudflare nameservers publish Google Workspace MX (ASPMX priority 1; ALT1/2 priority 5; ALT3/4 priority 10), apex SPF `v=spf1 include:spf.efwd.registrar-servers.com include:_spf.google.com ~all`, Google `google._domainkey` and Resend `resend._domainkey` TXT. `_dmarc.vyraxlabs.co.uk` has no TXT answer. No authenticated Vyrax mailbox is configured in the local Himalaya accounts. The intended address is `support@vyraxlabs.co.uk`, but receipt, replies, owner monitoring, and Resend acceptance/delivery have not been proven. An MX or DKIM record does not prove a provisioned mailbox or verified sending domain.

## Before enabling anything

1. Rotate any previously exposed Resend key and verify a **dedicated Vyrax** Resend account/domain/sender in its dashboard. Publish a DMARC policy in DNS after confirming Google Workspace and Resend alignment; confirm the actual sender's DKIM selector and SPF/return-path against the provider dashboard (the current DNS records alone do not establish either end-to-end result). Prove `support@vyraxlabs.co.uk` receives a controlled message, that a reply returns to a monitored owner inbox, and that an owner-approved preview from the Vyrax sender is accepted and delivered. Confirm legal footer facts before filling any `site.ts` nulls. Set `RESEND_API_KEY`, `VYRAX_EMAIL_FROM` and the owner-alert recipient as server secrets only. Do not set VITE-prefixed secrets.
2. For any future enquiry flow, add a server-side intake independent of the closed SpicePay checkout: validate current catalogue data, reprice the basket server-side, enforce abuse protection, and only return success after persistence. The former browser INSERT has already been removed. Trigger `renderEmail({ kind: "enquiry" | "ownerAlert", ... })` from the saved record, with `sendTransactional` and a stable key per event/record. Handle partial failures/retries with a durable outbox before promising acknowledgement. Only then consider `site.enquiriesLive = true`; keep payment checkout gates separate.
3. Hook payment and fulfilment templates **only** to authoritative, persisted paid/packed/dispatched/cancelled/refunded events, never to a user-submitted status or an enquiry. The existing signed webhook records payment state but does not send mail. Auth drafts require configuring the actual Supabase Auth email provider/templates and testing the provider action URL; the current `renderEmail` auth link allowlist accepts the Vyrax origin only. Support acknowledgement requires an actual message store and monitored support inbox.
4. Owner approves a preview sent only to their address, checks source/recipient and rendered mail, then approves any deploy/activation. Verify live paths separately; a successful build is not proof of delivered mail.

Run `bun test tests`, `bunx tsc --noEmit`, `bun run claims`, `bun run build`. This audit sends no mail and does not change DNS, secrets, schema, checkout flags, production deployment or publishing.
