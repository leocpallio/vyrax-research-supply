# Vyrax Labs email system: readiness and wiring

## Current status (code only, not deployed)

- `src/lib/email/templates.ts` renders HTML and plain text from one Vyrax brand wrapper. Ready: enquiry acknowledgement, owner enquiry alert, payment pending/confirmed, packed/dispatched, cancellation/refund, support acknowledgement and auth confirmation/reset drafts. All dynamic copy is escaped. Only verified same-origin auth links become clickable; external tracking links are deliberately not inserted blindly. Indicative enquiry prices are not receipts.
- `src/lib/email/send.server.ts` is a server-only Resend transport with an idempotency header. It fails closed without server environment `RESEND_API_KEY` and `VYRAX_EMAIL_FROM`, and requires the sender domain `vyraxlabs.co.uk`. No key is committed or used here. The key disclosed in chat must be rotated, not reused. Never use another brand's key.
- **No messages are wired live.** `site.email` is null and `site.enquiriesLive` is false; `/checkout` cannot accept enquiries. Existing direct Supabase insert sends no mail. `/contact` is a `mailto:` draft gated on `site.email`, not a contact submission. Account signup/confirmation currently belongs to Supabase Auth/Lovable Cloud, so these auth drafts do not replace provider mail automatically. There is no checkout payment integration, no paid-status event, no fulfilment transition event, no ticket store and no recovery automation. No marketing recovery template is provided, because there is no real checkout/payment state or unsubscribe infrastructure.

## Before enabling anything

1. Rotate the exposed Resend key and establish a **dedicated Vyrax** Resend account/domain/sender. Verify SPF/DKIM/DMARC, receiving support mailbox, reply path and owner-monitored inbox; confirm legal footer facts before filling any `site.ts` nulls. Set `RESEND_API_KEY`, `VYRAX_EMAIL_FROM` and an owner-alert recipient via server secrets only. Do not set VITE-prefixed secrets.
2. Replace direct browser `orders` insert with a server-side intake that validates the current catalogue and reprices the basket server-side, enforces abuse protection and only returns success after persistence. Trigger `renderEmail({ kind: "enquiry" | "ownerAlert", ... })` from the saved record, with `sendTransactional` using a stable key per event/record. Handle partial failures/retries with a durable outbox before promising acknowledgement. Only then consider `site.enquiriesLive = true` and update checkout/account copy. There is no trustworthy mail-trigger path in the existing client insert.
3. Hook other templates **only** to authoritative paid/packed/dispatched/cancelled/refunded events, never to a user-submitted status string or an enquiry. Auth drafts require configuring the actual Supabase Auth email provider/templates and testing the provider action URL; the current `renderEmail` auth link allowlist accepts the Vyrax origin only. Support acknowledgement requires an actual message store and monitored support inbox.
4. Owner approves a preview sent only to their address, checks source/recipient and rendered mail, then approves any deploy/activation. Verify live paths separately; a successful build is not proof of delivered mail.

Run `bun test tests`, `bunx tsc --noEmit`, `bun run claims`, `bun run build`. No preview, production send, secret-setting, schema change or deployment occurred in this branch.
